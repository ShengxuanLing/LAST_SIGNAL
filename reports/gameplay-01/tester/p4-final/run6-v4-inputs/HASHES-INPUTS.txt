## what changed (tests only; no product, no timeout, no assertion relaxation)

P4 (gameplay-04-coop-level):
  - the door jam no longer uses a fixed sleep. Before pressing Y it checks the REAL preconditions the
    core checks (GameScene active + only scene / not paused / no level-up overlay / world+camera /
    relay ACTIVE / jam CD 0 / energy>=25 / distance<=JAM_RANGE / LOS sampled at 0.25 with radius 0.5),
    then sends ONE keydown held until the stepFrame trace shows a processed tick AND a real
    signal-jammed event; keyup only after a further real frame; on a bounded timeout (5s) it records
    the full trace and fails explicitly (no retry, no second keydown).
  - added a read-only stepFrame trace (ticks per call, queue before/after, signal events, loop frame).
  - receipt semantics: the ECHO assertion no longer claims a fixed tick gap. It now asserts the
    committing stepFrame processed >=1 tick, the core queue held exactly this command in that batch,
    the queue never survived a whole batch, exactly ONE commit event, and audit applied > enqueued.
    The measured sim.tick gap (1, 2, 3 under load) is recorded, never asserted as a constant.
P2 (gameplay-02-echo-coop):
  - clearRoomByRealPlay keeps the 120 s wall budget but stops sleeping between inputs: every move/fire
    input is held until the simulation advanced >=1..3 real ticks (bounded wait), so the edge is
    consumed by real simulation frames. It also clears real overlays (level-up card) with a real click
    and records per-sample tick / hp / enemiesAlive / paused / levelUpActive / owner / relay / active
    scenes, plus stall events (input with no tick advance) in the evidence.
  - no teleport, no clearEnemies, no heal, no skip, no timeout change.

## classification

CONFIRMED by these runs:
  - with a tick-consumed Y edge, the door jam commits on the first processed batch after the press;
  - with tick-consumed inputs, both P2 tests clear the authored room in ~1.2-1.4 s at current load;
  - the ECHO command is enqueued and drained inside one stepFrame batch (queue never held across batches).
INFERENCE (not proven by these bytes):
  - that the earlier full-run failures were caused by key edges landing in frames that never processed a
    tick: the old driver did not record per-input tick progress, so its exact failure mechanism is
    reconstructed, not measured. The new drivers make that mechanism observable.
NOT CHANGED: product sources (10 manifest files), timeouts (20s/15s/120s), any assertion threshold,
  skip/fixme, model calls. No commit/push.
